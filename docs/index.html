“The application stays simple. The network is the project.”

What

A private service at app.teamX.test that exists only on our Wi-Fi: our own DNS, our own certificate authority, our own load balancer.

How

Four Macs, each standing in for a cloud service: dnsmasq as Route 53, nginx as the load balancer, two small Python REST backends.

Why

To prove every layer with dig, curl and Wireshark, break it on purpose, then make it survive DNS, backend and edge failures.

05 · How we built it

Four small configs, one working platform

Off-the-shelf tools configured by hand: dnsmasq, nginx and mkcert, plus about 60 lines of standard-library Python per backend.

Private DNS

Mac 1 · dnsmasq
listen-address=10.7.31.159
address=/app.teamX.test/10.7.4.179
address=/api.teamX.test/10.7.4.179
local-ttl=30            # Phase 1 was 0
server=8.8.8.8          # everything else → public DNS
Names in the reserved .test zone. .local would collide with macOS mDNS.

Edge & load balancer

Mac 2 · nginx
upstream backend_cluster {
  server 10.7.28.230:3001 max_fails=1 fail_timeout=10s;
  server 10.7.15.199:3002 max_fails=1 fail_timeout=10s;
}
listen 443 ssl;  http2 on;
proxy_next_upstream error timeout http_502;
Single entry point. Terminates TLS, then load-balances round-robin over plain HTTP.

Certificates

Mac 2 · mkcert CA
mkcert -install                  # our own root CA
mkcert -cert-file app.teamX.test.pem \
       -key-file  app.teamX.test-key.pem \
       app.teamX.test api.teamX.test
curl --cacert rootCA.pem https://app.teamX.test  # never -k
Every client trusts our root CA, so the certificate verifies for real.

Ext A · Backup DNS

Kill the DNS server. Keep the name.

Every client lists two resolvers: Mac 1 first, then Mac 4 with identical records.

DNS failure: the name disappears while hosts are still reachable by IP. Application failure: the name resolves, but the service errors (502, refused).
Ext B · TTL & controlled change

The client switched after ≈43 s against a 30 s TTL. A TTL is the minimum time an old answer may live, not a deadline. For a migration: lower the TTL first, cut over, wait, then raise it again.

  • 12:58:19client resolves and caches 10.7.4.179

  • 12:59:22records reverted → 10.7.4.179

Ext C · Service isolation

Only the edge may knock

macOS pf rules on Mac 3 and Mac 4 accept connections to 3001/3002 from 10.7.4.179 only. Everyone else gets an instant TCP reset.

Least privilege at the transport layer, the same idea as private subnets + security groups. TLS, logging and load balancing can no longer be bypassed. The rollback was planned before the rules went on.
Ext D · High-availability failover

Lose a backend, lose no requests

max_fails=1 fail_timeout=10s detects the failure; proxy_next_upstream retries the same request on the healthy backend.

Ext E · DNS-based edge migration

Move the edge with DNS alone

A standby nginx on Mac 3 with the same config and certificate. We changed one DNS record; the X-Edge header shows who answered.

  • 13:09:56standby tested with --resolve → mac3
  • 13:10:20Mac 1 → X-Edge: mac2
  • 13:10:23record → 10.7.28.230 · Mac 1 cached → mac2
  • 13:10:37Mac 4 (fresh) → X-Edge: mac3
  • 13:11:15Mac 1 cache expires → mac3
  • 13:11:53cut back → mac2
For about one TTL, two edges serve at the same time. Users notice nothing because both edges are identical and stateless. That is why production migrations keep the old edge running until its traffic drains.

Takeaways

What's still fragile, and what we learned

i
DNS is a directory, not a connection.A correct lookup can still send you to the wrong place.
ii
A TTL is a minimum, not a deadline.Plan migrations around the slowest cache.
iii
Failover = detection + retry.Marking a backend down is not enough; the failed request has to be retried.
iv
Isolate by default, keep a rollback.Only the edge talks to backends, and every rule change is reversible.
v
Debug in the order the packet travels.dig → ping → nc → openssl → curl → logs.
